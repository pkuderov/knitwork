### Что означает каждый результат

1. **Two reads — основной кандидат для подтверждения.** Выигрыш виден на всех 11 общих validation-точках после 100M и сохраняется при оценке с window1024. Весов столько же, сколько у dynamic-control, но вычислений больше: два candidate update центра вместо одного, примерно +25% cell projection arithmetic при C4. Нельзя называть это бесплатным улучшением или преимуществом при одинаковом compute. Следующий контроль должен отделить второй проход от адаптивного второго запроса.
2. **Write gate — небольшой, но последовательный эффект.** 11/12 общих точек после 100M лучше контроля; на 280M разница всего −0.001670. Последние логируемые layer means: L0 0.88304, L1 0.91111. Они включают hub с gate=1; средние только периферии составляют примерно 0.84405 и 0.88148. Среднее не доказывает содержательно-зависимую селекцию. Сравнить с постоянными gates около 0.85/0.88 прежде добавления сложного контроллера.
3. **Rotations — пока слишком маленькая разница.** Добавлено 24 угла; 7/11 общих точек лучше контроля, но поздний выигрыш лишь около 0.00135. Сначала повтор seed и проверка величины углов, затем решение о развитии. Не объявлять результат значимым по одной кривой.
4. **Query-read — текущая реализация проигрывает.** Ни одна из 11 общих точек после 100M не лучше контроля, несмотря на +57,600 весов. Замена полного сообщения реконструкцией через rank16 может ограничивать интерфейс памяти. Гипотеза следующей дешёвой проверки: residual read с обучаемым масштабом, начинающимся с нуля, и rank8. Это новая конфигурационная возможность, пока не реализованная.
5. **Associative — Text8-результат отрицательный, механизм ещё не опровергнут.** 0/10 выигранных точек, на 280M отставание +0.025629. Заменён целый LRU-столбец: меньше весов, больше состояния, другой тип памяти. Последние write rates около 0.9615/0.9183 показывают почти полные поправки в направлении текущего ключа; они не означают стирания всей матрицы. Проверить ограниченный write rate и retrieval-задачу MQAR, прежде чем увеличивать матрицу или запускать большой языковой sweep.

## Сравнение с Grid-GRU и обычной GRU

На одинаковой точке 980,037,632 токенов для seed42: Grid-GRU L2C4 1.592080, GRU L2 1.636439, исходный Grid-LRU L2C4 1.672669. Это по-прежнему не подтверждает превосходство LRU над GRU. Общая доступная точка сразу всех девяти кривых трёх seed-групп теперь 420,016,128: GRU 1.681285 ± 0.001875, Grid-GRU 1.650830 ± 0.004883, Grid-LRU 1.771913 ± 0.007261; ± означает sample standard deviation, n=3. Усреднять последние точки разных горизонтов как общий финальный результат нельзя.

**Уточнение предыдущего отчёта:** зарегистрированные коэффициенты Grid-GRU — communication 0.05, entropy 0.005, routing noise 0.05, и текущий код действительно использует эти terms. У Grid-LRU comm/entropy terms не возвращаются core и не применяются, даже если эти коэффициенты присутствуют в общей YAML. Формулировка предыдущего отчёта «общий протокол без дополнительных лоссов» относилась к LRU sparse-серии и была слишком широкой для Grid-GRU. Подготовленные абляции позволяют проверить эту асимметрию напрямую.

## MQAR и прочие новые запуски

В проекте видны два MQAR-запуска, dynamic-control и write-gate, с сокращённым бюджетом 8 epochs вместо стандартных 32. Пока у обоих есть только training metrics примерно на 1,001,472 токенах: train accuracy около 0.02%, train CE около 8.47, logged skipped_steps=0. Validation и test ещё не появились, поэтому сравнительного вывода по MQAR нет. Логируемый `train/update` сглаживается tracker и не является точным счётчиком optimizer updates.

Mamba пока имеет только около 15M токенов и training metrics, без validation. Новые seeds L3 GRU/Grid-GRU ещё не дошли до общего позднего горизонта. Они не меняют основной вывод и не должны смешиваться с завершёнными 1B-запусками.

## Приоритет следующих экспериментов

1. Дождаться окончания нынешней новой серии; дополнительные seeds 1337/31337 для two_reads и dynamic-control. В контроле второго чтения сохранить свежие периферийные сообщения и compute, но использовать прежний hub query, чтобы отделить пользу итеративного запроса.
2. Минимальная серия rollout64/512 для Grid-GRU/Grid-LRU, затем обычные GRU/LRU. Держать одинаковое число токенов на update, per-token reset schedule и validation streams. Это проверка длины градиента, а не изменение архитектуры.
3. Grid-GRU full против none, затем одиночные выключения noise/communication/entropy. Не начинать с восьми combinations × всех rollout × трёх seeds.
4. Для write-gate — fixed-gate control прежде нового контроллера. Для query-read — один residual/rank8 вариант; для associative — один ограниченный write-rate вариант на MQAR. Эти механистические контроли пока являются предложениями, не готовыми конфигами.
5. Отдельно измерить GPU time и peak memory у двухшагового чтения после стабилизации качества. GPU inventory и logging fps на общей занятой машине не устанавливают speedup.

Готовые экономные rollout/regularizer-конфигурации и команды: [отдельный план запуска](2026-10-03-rollout-and-grnn-ablation-plan.md). Новых долгих запусков, публикационных утверждений и изменений статьи этот анализ не выполняет.

## Проверяемость

Снимок получен несколькими read-only запросами и не атомарен. Пропуски validation не интерполируются. Дубликаты validation дедуплицированы по последнему timestamp, конфликтующих значений на повторных шагах не обнаружено. Исходный commit не зарегистрирован ни у одного из 43 запусков: соответствие текущему локальному коду не доказано. В анализе используются параметры активной модели, а не неиспользуемые разделы общей YAML. Одного seed недостаточно для выводов о статистической значимости или специализации колонок.
