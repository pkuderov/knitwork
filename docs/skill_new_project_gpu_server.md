## 1. Видеокарты — характеристики и политика использования

Проверено `nvidia-smi` напрямую на сервере (2026-07-28):

| Индекс | Модель | Память | Driver | Макс. поддерживаемая CUDA (рантайм) |
|---|---|---|---|---|
| 0 | Tesla V100-SXM3-32GB | 32768 MiB | 580.159.03 | 13.0 |
| 1 | Tesla V100-SXM3-32GB | 32768 MiB | 580.159.03 | 13.0 |
| 2 | Tesla V100-SXM3-32GB | 32768 MiB | 580.159.03 | 13.0 |
| 3 | Tesla V100-SXM3-32GB | 32768 MiB | 580.159.03 | 13.0 |

Все 4 карты физически одинаковые (V100-SXM3, 32GB, compute capability 7.0). Driver поддерживает CUDA
**до 13.0 включительно** — это верхняя граница, а не то, что обязательно нужно ставить: любой более
старый CUDA-рантайм в PyTorch-колесе (cu118, cu121, cu124, cu126...) будет работать благодаря
обратной совместимости NVIDIA-драйверов. В этом же проекте (`vladimir-dev`) уже подтверждённо
работает `torch==2.6.0+cu118` на этом самом сервере — можно использовать как проверенную базовую
точку, если новый репозиторий сам не диктует что-то другое.

**Политика распределения GPU (важно, не менять самовольно):**
- Индексы **0, 1, 2** — для проекта `vladimir-dev` (LISA), можно использовать и для нового проекта
  в подпапке `vladimir-dev/<новая-подпапка>/`, поскольку это тот же "слот" на сервере.
- Индекс **3** — зарезервирован для других участников. **Никогда не использовать.**
- **Перед каждым запуском** обязательно проверять:
  ```
  nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv
  ```
  и выбирать реально свободный индекс из {0,1,2} — другие участники могут уже использовать один из
  них в любой момент, это не статическая гарантия свободного железа.
- Указывать `CUDA_VISIBLE_DEVICES=<индекс>` перед запуском любого torch-процесса.
- **Параллельные эксперименты на одной карте**: желательно запускать **до 6 экспериментов
  одновременно на одной физической карте** (32GB достаточно для нескольких лёгких прогонов сразу,
  например для этого проекта одиночный `lisa-train`-процесс занимал ~5GB). Это ориентир, а не жёсткая
  гарантия — перед добавлением каждого следующего параллельного прогона на ту же карту заново
  смотреть `nvidia-smi --query-gpu=memory.used,memory.total --format=csv` и убеждаться, что
  оставшейся памяти хватает с запасом (крупные модели/большие батчи могут не позволить дойти до 6).

## 1.5. Параллельные `git pull` в `vladimir-dev/` и в подпапке — безопасны, проверено

`vladimir-dev/` сама по себе — git-репозиторий (клон приватного LISA-репо). Новая подпапка
(`vladimir-dev/<новая-подпапка>/`) — **отдельный** git-репозиторий (свой `.git/`) внутри рабочего
дерева первого. Это может выглядеть рискованно (не перепутает ли внешний `git pull` файлы вложенной
репы?) — проверено напрямую на сервере, реального конфликта нет:

- Директория со своим `.git/` видна внешнему репозиторию как **один** untracked-элемент в
  `git status` (`?? <новая-подпапка>/`), git **не заходит внутрь** и не отслеживает её содержимое
  файл-за-файлом.
- `git pull` во внешнем репозитории (`vladimir-dev/`) не трогает, не блокирует и не конфликтует с
  содержимым вложенной репы — проверено вживую (создана тестовая вложенная репа с коммитом, запущен
  `git pull` снаружи, содержимое вложенной репы осталось полностью нетронутым).
- У каждого git-репозитория свой собственный `.git/index.lock` — они физически не пересекаются, так
  что `git pull` во внешней репе и `git pull` внутри подпапки можно запускать **в любом порядке и
  даже одновременно** из разных SSH-сессий, без риска гонки за один и тот же lock-файл.
- Единственная (некритичная) деталь гигиены: подпапка будет постоянно маячить как untracked в
  `git status` внешней репы. Если это мешает — добавить её имя в `vladimir-dev/.gitignore` (текущий
  `.gitignore` не содержит wildcard-правила для произвольных новых подпапок — проверено). Это **не
  обязательно** для безопасности пуллов, только для чистоты `git status`.

## 2. Затащить публичный репозиторий в подпапку внутри `vladimir-dev`

Публичный репозиторий не требует токенов/deploy-ключей — обычный `git clone` по HTTPS работает сразу:

```
cd ~/Spatial-Attention-Project/vladimir-dev
git clone https://github.com/<owner>/<repo>.git <новая-подпапка>
```

- `<новая-подпапка>` — например `knitwork` (по имени проекта/Comet-проекта, для консистентности).
- Результат: `~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/` — полноценный клон со своей
  историей git, независимый от LISA-клона на уровень выше.
- Если позже понадобится push в этот репозиторий (не только pull) — see `agent.md §6/§7.2` в основном
  проекте за паттерном PAT/deploy-key принятия решений; для публичного read-only использования это не
  нужно вообще.

## 3. Своё окружение из `pyproject.toml` нового репозитория

Тот же паттерн, что уже используется для `vladimir-dev/.env` (project-local conda prefix env —
**не** именованный env в `~/miniforge3/envs/`, чтобы не столкнуться в общем namespace с другими
участниками):

```
~/miniforge3/bin/conda create --prefix ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env python=3.11 pip -y
~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env/bin/python -m pip install -U pip
```

**Перед установкой PyTorch/CUDA-пакетов** — открыть `pyproject.toml` (или `requirements.txt`,
`scripts/setup_*.sh`) нового репозитория и посмотреть, как там объявлен torch:
- Если версия torch зафиксирована с явным `--index-url .../whl/cuXXX` — оставить как есть, если
  `cuXXX <= cu130`-эквивалент (driver это позволяет).
- Если версия CUDA в исходном index-url **новее**, чем поддерживает driver (маловероятно здесь, т.к.
  driver поддерживает вплоть до 13.0 — почти любая современная сборка подойдёт) — заменить на ближайшую
  доступную сборку с PyTorch-индекса: `https://download.pytorch.org/whl/cu118` /`cu121`/`cu124`/`cu126`
  и т.д. (проверить актуальный список на pytorch.org — какие сборки существуют для нужной версии
  torch).
- Пример установки (адаптировать версию torch/CUDA под то, что требует репозиторий):
  ```
  ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env/bin/python -m pip install torch==<версия> --index-url https://download.pytorch.org/whl/cu118
  ```
- Если в `pyproject.toml` есть другие CUDA-зависимые пакеты (`onnxruntime-gpu`, `faiss-gpu`,
  `cupy-cudaXXx`, `flash-attn` и т.п.) — их версии/wheel-суффиксы тоже должны соответствовать
  выбранной CUDA-сборке torch, а не абстрактной "версии карты" (сама модель карты, V100, тут не
  играет роли — важна только версия CUDA в установленных wheel'ах против того, что поддерживает
  driver).
- Затем сам пакет из его собственного `pyproject.toml`:
  ```
  cd ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>
  ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env/bin/python -m pip install -e .
  ```
  (или `-e ".[extras]"`, если в проекте есть extras-группы, аналогично `.[clearml,comet,dev]` в
  LISA).
- **Обязательная проверка после установки**:
  ```
  ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env/bin/python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.device_count())"
  ```
  Ожидается `True` и `4` (или сколько видно без `CUDA_VISIBLE_DEVICES`-ограничения).

## 4. Логирование экспериментов в Comet, проект `knitwork`

Comet API-ключ **уже настроен** на сервере на уровне аккаунта (`~/.comet.config`, секция `[comet]`,
`api_key=...`) — **не создавать новый ключ**, он общий для всего аккаунта `User5` и уже привязан к
рабочему пространству (workspace) `adran-dasadfan` на comet.com, которое уже используется проектом
LISA (project `meg_emb`). Проект `knitwork` — это просто **другое имя проекта** в том же workspace;
Comet создаёт его автоматически при первом логировании, регистрировать заранее не нужно.

- Если у нового репозитория уже есть свой CLI-флаг вида `--logging-project`/`--comet-project` —
  просто передать `knitwork` в него.
- Если логирование делается напрямую через `comet_ml` в коде — указать `project_name="knitwork"` в
  `comet_ml.start(...)` / `Experiment(...)`.
- Если через переменную окружения — `COMET_PROJECT_NAME=knitwork` перед запуском команды.
- Убедиться, что установлен пакет `comet-ml` именно в **новом** `.env` (`<новая-подпапка>/.env`), не
  предполагать, что он "виден" из окружения `vladimir-dev/.env` — окружения полностью раздельные.
  ```
  ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>/.env/bin/python -m pip install comet-ml
  ```

## 5. Запуск с фоновым выполнением (устойчивость к обрыву SSH)

Тот же паттерн, что и для LISA-экспериментов — `nohup ... & disown`, вывод в файл, не в терминал:

```
cd ~/Spatial-Attention-Project/vladimir-dev/<новая-подпапка>
CUDA_VISIBLE_DEVICES=<0|1|2> nohup .env/bin/python <entrypoint> <args> > /tmp/<run-name>.log 2>&1 < /dev/null & disown
```

Проверять прогресс через `tail -n N /tmp/<run-name>.log`, статус процесса — по PID (не по `pgrep -f`
с текстовым паттерном мониторящей команды — если сама команда мониторинга содержит тот же паттерн в
своей командной строке, она находит саму себя; использовать `kill -0 <PID> 2>/dev/null` вместо этого).
