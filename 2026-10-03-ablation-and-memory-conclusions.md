### Почему эффект на BPC мал

- **Аблируются noise и penalties, а не столбцы/связи/readout.** Основной информационный путь остаётся. Поэтому близкий BPC говорит об этих регуляризаторах, не о бесполезности модульной памяти.
- **Noise0.05 в attention logits — небольшое возмущение; entropy coefficient0.005 ещё слабее.** При H≈0.97 entropy term около0.0048 nats. Кроме того, entropy уже близка к максимуму; её производная по logits мала возле равномерного распределения. Из этого нельзя выводить точный относительный gradient вклад на обученных весах без отдельного измерения.
- **Текущий entropy term поощряет размазывание attention:**он вычитается из objective. Communication term предпочитает некоторые пути/self/external маршруты, но не определяет, какой столбец хранит какую семантику. Эти objectives не гарантируют полезную специализацию.
- **Серия очень ранняя.** TBPTT64, всего три общие оценки, reset-warmup100×15 updates≈49.15M tokens; общая точка50.33M лишь немного после конца этого warmup. В таких условиях длинная защищённая память ещё слабо проверена. Hypothesis:Text8 BPC в этом режиме достаточно хорошо объясняется локальным контекстом и ёмкостью ячеек.
- **Компенсация остальными проекциями вероятна:**модель может изменять представления при изменённом routing и сохранять предсказания. Это гипотеза, а не установленная причинная связь. Низкая cosine similarity столбцов сама по себе также не доказывает различие их функций.

## Принципиально иной подход для Grid: адресуемые записи с защитой от перезаписи

**Предложение для следующего прототипа:первый столбец — рабочий recurrent controller, периферия — фиксированные банки отдельных key/value записей.** Сохранить именно выбранный bottleneck:output и task head получают только первый столбец. Hub формирует адрес чтения, содержимое записи и решение о записи; прочитанные записи возвращаются в hub. Длительная память не обязана каждый token проходить полный recurrent update и смешивание с новыми входами.

Порядок шага:

1. Hub обрабатывает текущий token и формирует query.
2. Query читает несколько записей по совпадению ключей; hub уточняет свою рабочую память и выдаёт prediction. Чтение происходит до записи, чтобы при query не разрушать запрашиваемый факт.
3. Отдельный write address направляет запись в один/несколько слотов; невыбранные записи сохраняются. Повтор того же ключа может обновить его значение, новый факт — занять свободный/выбранный слот. На pure-read token write gate может закрываться.
4. Slot bank имеет фиксированный размер, reset/detach следуют общему протоколу. Только обычный task loss, без losses на diversity/специализацию.

Простейший update для значения слота j:`V[j]←(1−w[j])V[j]+w[j]v`, аналогично для key. При w[j]=0 запись сохраняется в точности. Для первого differentiable прототипа начать с soft addressing и малого числа слотов, отдельно измерить размазывание writes; разреженный top1/top2 forward требует осознанного решения о gradients/straight-through и не получает бесплатной гарантии обучаемости. До этого не обещать exact protection всех невыбранных записей при dense-soft writes. Добавить маленький ненулевой масштаб memory-read branch, чтобы не разрушить исходный hub и оставить gradients к памяти.

Отличие от нынешнего associative:там много associations накладываются на одну16×32 матрицу; здесь хранятся **отдельные адресуемые записи**, и новый token не обязан влиять на все старые факты. Отличие от write_gate:gate выбирает, какую запись менять, а не только тормозит весь LRU-вектор. Отличие от two_reads:меняется устройство persistent storage, а не только число циклов чтения. Контент и адрес памяти разделяются; hub должен научиться извлекать полезную информацию через тот же первый столбец.

Это новый для проекта архитектурный путь, **не заявление о новой мировой идее**:content-addressed read/write и allocation имеют прямых предшественников в [Neural Turing Machines](https://arxiv.org/abs/1410.5401) и [DNC](https://www.nature.com/articles/nature20101). Для вероятного преимущества над Mamba на retrieval есть мотивация:отдельные записи позволяют ограничить interference при записи отвлекающих tokens. [Gated DeltaNet](https://arxiv.org/abs/2412.06464) уже показывает, что изменение memory update/overwrite rule может улучшать retrieval и некоторые другие benchmarks относительно Mamba2; это основание исследовать storage, не доказательство преимущества предложенного Grid.

**Ожидаемый выигрыш сначала проверять на памяти, не обещать на Text8:**MQAR с ростом K и delay, distractors, повторной записью того же ключа; затем SDQ/Autoencode. Исходные MQAR cases оставить для сопоставимости, отдельно добавить overwrite/distractor probes, если прототип будет одобрен. Для прототипа достаточно малого bank budget, например3 banks×8 slots с key16/value32 =1152 floats только для записей; полный state включает hub/keys/feedback/metadata и должен измеряться отдельно. K64 при24 слотах может превысить capacity, поэтому сообщать всю capacity curve, не выбирать только удобный K.

Сравнить с текущим two_reads и **официальным Mamba/Mamba2**, отдельно фиксируя параметры, весь persistent-state budget, tokens/updates, wall time и peak memory. Нынешний [локальный Mamba core](knitwork/models/baseline/mamba.py) — компактная recurrent реализация, не воспроизведение всего официального training stack или fused kernels. Explicit slots могут улучшить адресацию, но потребуют allocator/write learning, имеют ограниченную capacity и могут проиграть по скорости. Превосходство Mamba по language modeling или compute пока не следует ни из этой гипотезы, ни из текущих результатов.

Прототип и дополнительные experiments здесь **не реализуются и не запускаются**:это предложение к обсуждению. Независимые seeds понадобятся для подтверждения результатов; текущие одиночные кривые дают направление и диагностику, а не significance.
