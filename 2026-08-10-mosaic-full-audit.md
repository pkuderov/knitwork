## Топ-5 обязательных правок

1. 🔴 **Разное число токенов у сравниваемых моделей.** В Table 1 базовые GRU остановлены на
   970/980/990 M, а MoSAIC — на 985/1000/1000/1000/1000 M. То же в Table 2. Заявленный
   контроль «one-billion-token training» не выполнен, и расхождение систематически в пользу
   предложенной модели. Это первая вещь, которую увидит рецензент.
2. 🔴 **Метрика Acc++ определена через плавающий порог** («gaps above the current batch
   mean»). Порог зависит от батча и дрейфует вместе с curriculum, поэтому число не является
   воспроизводимой характеристикой модели. Нужна оценка на фиксированном held-out наборе с
   фиксированными порогами разрыва.
3. 🟠 **Асимметрия настройки гиперпараметров.** MoSAIC имеет три обучающих регуляризатора
   (λ_comm, λ_ent, σ_ε) с подобранными значениями, различающимися между text8 и SDQ; GRU и
   Transformer получили один общий LR-график без подбора. Абляций регуляризаторов нет.
4. 🟠 **Figure 2 нигде не упомянут в тексте.** Единственное вхождение «Figure 2» — сама
   подпись. Это классический «висячий рисунок».
5. 🟠 **Отсутствуют близкие по духу базовые линии (RIMs / BRIMs / RMC).** Related Work
   строит позиционирование именно против них, а эмпирически сравнение идёт только с
   монолитным GRU. Заявленные HGRN2 / DeltaNet / mLSTM упомянуты, но не приведено ни одного
   их числа.

## Детальный разбор

### 🔴 C-1 · Несовпадающий бюджет токенов (Experiments, Table 1–2, Abstract)

**Где.** Table 1: GRU-L1 970 M, GRU-L2 980 M, GRU-L3 990 M против MoSAIC-L1C8 1000 M,
L2C4 985 M, L2C8 1000 M, L2C16 1000 M, L3C4 1000 M. Table 2: GRU-L1 980 M, GRU-L3 980 M,
Transformer cache-64 962.6 M против пяти конфигураций MoSAIC на 1000 M.

**Проблема.** Средний бюджет базовых GRU в Table 1 — 980 M, у MoSAIC — 997 M. Направление
расхождения совпадает с направлением заявленного улучшения. Кроме того, «logging-loss
convention», на которую ссылается оправдание («retained only under the documented
logging-loss convention»), в статье **нигде не описана** — слово «documented» отсылает к
документу, которого читатель не видит.

**Что скажет рецензент.** «The proposed model was trained on up to 3 % more tokens than the
baselines it is compared against, and the convention used to retain shorter runs is not
defined in the paper.»

**Как чинить (по убыванию предпочтительности).**
1. Дообучить/переоценить все конфигурации в одной общей точке и сообщить единый бюджет.
2. Оценить все модели в **минимальной общей точке** (962.6 M) и привести таблицу к ней —
   это делается из уже сохранённых логов, без новых прогонов.
3. Минимум: определить logging-loss convention прямо в тексте и добавить колонку
   «Δ tokens vs baseline», явно проговорив направление смещения.

### 🔴 C-2 · Метрика Acc++ имеет плавающий порог (Experiments → SDQ → Metric)

**Где.** «The code logs Acc++ as query accuracy on examples whose valid store–query gaps are
above the current batch mean.»

**Проблема.** Три отдельных дефекта в одном определении:
1. Порог — среднее по **текущему батчу**, то есть случайная величина, меняющаяся от батча
   к батчу.
2. Curriculum меняет среднюю длину эпизода с 10 до 500 в ходе обучения, значит **смысл
   метрики дрейфует по ходу самого обучения**; «финальные пять точек» усредняют значения
   с разными порогами.
3. Метрика вычисляется онлайн на обучающем потоке — отдельного held-out набора для SDQ нет.

Формулировка «The code logs…» дополнительно показывает, что метрика унаследована от
реализации, а не сконструирована под задачу.

**Как чинить.** Зафиксировать оценочный набор SDQ (фиксированный seed, фиксированное
распределение эпизодов) и сообщать точность по фиксированным корзинам разрыва, например
gap ∈ (0,50], (50,200], >200. Это даёт и воспроизводимость, и более сильный аргумент:
преимущество по длинным разрывам станет видно напрямую, а не через прокси.
Старую метрику можно оставить как кривую обучения в Figure 2.

### 🟠 M-1 · Асимметричная настройка гиперпараметров

**Где.** Method: «(λ_comm, λ_ent, σ_ε) = (0.05, 0.005, 0.05)» для text8 и «(0.02, 0.002,
0.02)» для SDQ. Experiments: все модели используют «the same learning-rate schedule».

**Проблема.** MoSAIC получил три дополнительных гиперпараметра, подобранных **отдельно под
каждую задачу**; GRU и Transformer не получили никакого подбора. Одновременно раздел
Limitations признаёт, что эффекты этих членов не изолированы. Рецензент соединит два факта:
преимущество может частично объясняться тем, что настраивали только одну сторону.

**Как чинить.** Либо (a) добавить строку MoSAIC-L2C4 **без** всех трёх регуляризаторов
(λ = 0, σ = 0) в обе таблицы — это один прогон на задачу и он закрывает возражение почти
полностью, либо (b) явно сообщить бюджет подбора для каждой семьи и показать, что для GRU
подбор LR не даёт улучшения.

### 🟠 M-3 · Нет ни одной модульной базовой линии

Related Work выстраивает позиционирование против RIMs, BRIMs, Shared Workspace и Relational
Memory Core, объясняя отличие («dense synchronous updates», «learned routing, not sparse or
conditional computation»). Эмпирически же MoSAIC сравнивается только с монолитным GRU и
Transformer. Утверждение «плотный роутинг лучше разреженного выбора экспертов» ниоткуда не
следует, хотя текст дважды на него намекает.

**Как чинить.** Минимально достаточный вариант — **абляция внутри собственной архитектуры**,
а не чужая реализация: MoSAIC-L2C4 с top-k роутингом (k = 1) вместо плотного softmax, при
том же бюджете. Это прямой ответ на вопрос «а нужен ли плотный роутинг» и стоит одного
прогона на задачу. Полноценная реимплементация RIMs не обязательна, если это оговорено.

### 🟠 M-4 · Базовые линии, для которых не приведено ни одного числа

Related Work и «Reduced-token baselines» упоминают HGRN2, DeltaNet и mLSTM, сообщают, что
они не влезли в память при 512 потоках, и что выводы из них не делаются. В итоге читатель
получает три названия и ноль данных.

объяснение: число потоков можно уменьшить с компенсацией шагов накопления градиента, сохранив
токенный бюджет. Рецензент это предложит.

**Как чинить.** Либо привести их числа в приложении с явной пометкой о разном бюджете, либо
перепрогнать при 128 потоках × 4 шага накопления и включить в основную таблицу. Третий
вариант — убрать упоминания совсем; текущее промежуточное состояние — худшее из трёх.

### 🟠 M-6 · Abstract сравнивает с не самым сильным GRU на SDQ

**Где.** «L2C4 obtains 0.843 ± 0.006 … versus 0.547 ± 0.077 for a two-layer GRU».

По Table 1 сильнейший GRU на SDQ — это **L1 с 0.6177**, а не L2 с 0.5465. При этом для text8
в том же Abstract используется корректная формулировка «for the strongest GRU». Асимметрия
бросается в глаза: там, где базовая линия слабее, выбрана «согласованная по глубине», там,
где сильнее — «сильнейшая».

Само по себе сравнение при равной глубине законно, но в Abstract оно выглядит как отбор
удобного числа. Тем более что настоящий результат никак не пострадает: 0.843 против 0.618
всё равно огромный отрыв.

**Предлагаемая замена:**
> On Store–Distract–Query, L2C4 obtains 0.843 ± 0.006 long-gap final-window accuracy against
> 0.547 ± 0.077 for a depth-matched GRU and 0.618 ± 0.005 for the strongest GRU baseline,
> while L3C4 obtains 0.920 ± 0.013.

### 🟠 M-7 · Привилегированная колонка 0 нигде не обсуждается

Два независимых решения делают колонку 0 особенной:
1. «The prediction head reads column 0 of the top layer.»
2. Стоимость маршрута для внешнего входа равна **2c** при нумерации с нуля, то есть для
   c = 0 вход бесплатен, а для c = 15 стоит 30 — сильнее, чем любой рекуррентный маршрут.

То есть колонка 0 одновременно является выходом и единственной, кому дёшево читать вход.
Это существенное архитектурное решение, поданное как деталь. Оно же может объяснять,
почему L2C16 хуже L2C4: при 16 колонках штраф 2c душит доступ к входу для большинства колонок.

**Как чинить.** Проговорить дизайн явно (2–3 предложения о том, зачем нужен именно такой
d^l_{c,j}) и связать с наблюдением из «Topology and State Allocation». Если есть прогон с
d = const, привести его — он объяснил бы главный неожиданный результат таблицы.

### 🟠 M-10 · Отклонение от стандартного разбиения text8

Использовано 90 M / 10 M (train / valid), тогда как общепринятое разбиение text8 —
90 M / 5 M / 5 M с отчётом по последним 5 M как по тесту. Плюс валидация использовалась для
ручного подбора. В результате приведённые BPC **не сопоставимы** ни с одной опубликованной
цифрой по text8.

Статья это частично признаёт («we call the metric validation BPC rather than an untouched
test estimate»), но не говорит главного — что и сравнение с литературой невозможно.
