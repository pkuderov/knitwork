### 0.1. Почему `run.py`, а не `run_sdq.py`/`run_text.py`

Проверено напрямую по коду. `run_sdq.py` резолвит
`rnn_type = config['model']`, `rnn_cfg = config['models'][rnn_type]`; при
`--model=grnn` это даёт `knitwork.models.grnn.GridRnn` — защищённый файл без
`communication`/`entropy`/`noise_std` вообще (проверено `grep`'ом по файлу).

Числа статьи считались `knitwork/exps/sdq/run.py` и
`knitwork/exps/text/run.py` (подтверждено `docs/reviews/grnn_core_analysis.md
§6` и git log `large.yaml`: коммит `17aca10 reduce comm loss and noise for
grnn on sdq`). В `run.py`:

```python
config['model_cfg'] = config['model'].replace('.', '_')   # "grnn.L2C4" -> "grnn_L2C4"
config['model']     = config['model'].split('.', 1)[0]    # "grnn.L2C4" -> "grnn"
model = build_model(..., rnn_type=config['model'], rnn_cfg=config[config['model_cfg']])
communication_cfg   = config.get('communication', {})
comm_loss_weight    = float(communication_cfg.get('loss_weight', 0.0))
comm_entropy_weight = float(communication_cfg.get('entropy_weight', 0.0))
```

Реестр — `knitwork/models/utils.py::REGISTRY`: `'grnn': 'grnn_core.GridRnn'`
(модуль с `noise_std`; регуляторы коммуникации/энтропии считаются снаружи, в
`run.py`). Реестр содержит ровно 6 активных записей: `rnn`, `grnn`,
`delta_net`, `hgrn2`, `mlstm`, `transformer` — ровно те семейства, что в
Table 1/2/3. **Все команды ниже — только `run.py` + `config/large.yaml`,
селектор вида `--model=grnn.L2C4` (точка, код сам конвертирует `.`→`_`).**

## 1. Задача D1 — пересчёт Table 1/2 на едином token-budget

**Это не новый эксперимент, а переобработка данных уже завершённых
прогонов** — явно вынесена отдельно от E1-E4, т.к. не требует GPU вообще, но
и не является чисто текстовой правкой (отличие от файла
`text-and-format-fixes.md`).

**Код: не реализован.** Нужен новый скрипт (или дополнение к
`inference/comet_aaai_snapshot.py`, не трогая его — он используется как
источник для `docs/experiments/results_aaai.md`).

**Что делает:**
1. Для каждого завершённого прогона в `knitwork-sdq`/`knitwork-text`
   вытягивает **полную историю** метрики (`Acc++`/`val/BPC`) по шагам через
   `comet_ml.api` — не `get_metrics_summary()` (даёт только финальную/лучшую
   точку), а отдельный вызов, возвращающий весь time series.
2. Находит `token_cutoff = min(конечный шаг по всем прогонам, участвующим в
   конкретной таблице)` — отдельно для Table 1 (SDQ) и Table 2 (text8).
3. Для каждого прогона берёт значение метрики в точке, ближайшей к
   `token_cutoff` (интерполяция не нужна — шаг логирования ~5M токенов по
   `log.schedule: 5.0e+6` в `large.yaml`, ошибка привязки — доли процента от
   1B).
4. Агрегирует mean/std по репликам.

**Ресурсы:** не требует GPU. Несколько часов работы на Python-скрипте +
доступ к Comet REST/`comet_ml.api` (ключ уже есть).

**Бюджет/гиперпараметры:** неприменимо (не обучение).

**Почему это нужно.** Table 1 сейчас: GRU — 970/980/990M, MoSAIC —
985/1000/1000/1000/1000M (расхождение систематически в пользу MoSAIC).
Рецензенты AAAI-27 это не заметили (3% — мало), но именно поэтому риск для
AISTATS асимметричен: новый набор рецензентов может заметить то, что
пропустили предыдущие, и направление расхождения работает в пользу
заявленного результата — находка такого рода меняет то, как рецензент
читает весь остальной текст. Дешёвый фикс (нет нового обучения) с
несоразмерно большим риском, если его не сделать.

## 2. Эксперимент E1 — ablation регуляторов коммуникации (M-1)

**Код: реализован, запуск — просто override конфига.**

**Модель и гиперпараметры:** `grnn.L2C4` (компактная референсная форма).
Базовые значения из `large.yaml` (SDQ): `hidden_size=424, n_layers=2,
n_columns=4, n_attn_heads=4, ln_msg=true, bank=2, mha=2, noise_std=0.02`,
глобально `communication.loss_weight=0.02, communication.entropy_weight=
0.002`. Для text8: те же структурные параметры, `noise_std=0.05`,
`communication.loss_weight=0.05, communication.entropy_weight=0.005`.

**Для ablation — override, выключающий все три регулятора:**
`communication.loss_weight=0`, `communication.entropy_weight=0`,
`grnn_L2C4.noise_std=0`.

**Бюджет:** `n_steps=1.0e9` (как в основных таблицах статьи), `n_envs=512`,
`rollout_len=32` (SDQ) / `64` (text8).

**Команды (две, SDQ + text8):**
```sh
ssh aicenter3 'cd /storage/annenkov_vd/knitwork && CUDA_VISIBLE_DEVICES=3 \
  nohup .venv/bin/python knitwork/exps/sdq/run.py \
  knitwork/exps/sdq/config/large.yaml --model=grnn.L2C4 \
  communication.loss_weight=0 communication.entropy_weight=0 \
  grnn_L2C4.noise_std=0 name="grnn_L2C4_noaux_sdq_E1" \
  > /storage/annenkov_vd/knitwork/logs/E1_sdq.log 2>&1 &'

ssh aicenter3 'cd /storage/annenkov_vd/knitwork && CUDA_VISIBLE_DEVICES=3 \
  nohup .venv/bin/python knitwork/exps/text/run.py \
  knitwork/exps/text/config/large.yaml --model=grnn.L2C4 \
  communication.loss_weight=0 communication.entropy_weight=0 \
  grnn_L2C4.noise_std=0 name="grnn_L2C4_noaux_text8_E1" \
  > /storage/annenkov_vd/knitwork/logs/E1_text8.log 2>&1 &'
```

**Ожидаемые ресурсы:** 2 прогона, модель ~10M параметров. На H100 (см. §6)
— ориентировочно 25-50 минут на прогон при консервативной оценке ускорения
×3 от референсного fps RTX 3050 (120-240k fps → ×3 ≈ 360-720k fps,
`1e9/540k ≈ 31 мин` в среднем); требует подтверждения реальным замером (см.
§6, п.1). VRAM — доли GB, не является узким местом на H100 80GB.

**Опциональное расширение (E1-ext, если время позволяет):** те же два
прогона с `--model=grnn.L3C4` (лучшая форма) вместо `L2C4` —
`grnn_L3C4.noise_std=0` в override, остальное аналогично.

**Что смотреть после старта** (метрики уже логируются существующим кодом):
`H_comm` (ожидание: не падает почти в ноль на SDQ без noise/entropy, если
гипотеза верна), `attn_beta/L*` (ожидание: не уходит в десятки), `col_sim/
avg` на text8 (ожидание: растёт быстрее, чем в контрольном прогоне с
регуляторами).

**Почему это нужно.** Все три человеческих рецензента и AI-Reviewer просят
ablation регуляторов — у MoSAIC три степени свободы регуляризации
(`λ_comm`, `λ_ent`, `noise_std`), подобранные отдельно под каждую задачу, у
GRU/Transformer — ни одной. Без этого шага стандартная логика атрибуции
результата (можно ли отделить вклад архитектуры от вклада регуляризации)
не выполнена. Дополнительно, по `docs/reviews/grnn_core_analysis.md` §4.1, у
отключения регуляторов есть конкретный, независимо измеримый ожидаемый
эффект (коллапс роутера) — если подтвердится, ответ получится сильнее, чем
формально запрошенный ablation-номер: механистическое объяснение, а не
просто «стало хуже».

## 3. Эксперимент E2 — held-out Acc++ с фиксированными gap-корзинами (C-2)

**Код: НЕ реализован.** Два отдельных требования:
a. `knitwork/exps/sdq/run.py` **не сохраняет чекпоинты весов** (проверено
   `grep`'ом по `checkpoint`/`ckpt`/`save(` — ноль совпадений) — значит
   нельзя дообразить метрику по старым весам, нужен полностью новый прогон с
   новым протоколом оценки.
b. Текущая метрика `Acc++` считается относительно плавающего порога («выше
   среднего по текущему батчу») — нужно добавить: фиксированный held-out
   генератор (`StoreDistractQueryGenerator` с зафиксированным `seed` и
   распределением эпизодов, не зависящим от текущего прогресса curriculum) +
   логирование по корзинам `gap ∈ (0,50], (50,200], >200` вместо текущего
   динамического порога.

**Модели и гиперпараметры:** три прогона — `grnn.L2C4`, `grnn.L3C4` (те же
параметры, что в E1, но **без** обнуления регуляторов — это полноценные
контрольные прогоны, не ablation), и `rnn.L1` (GRU-baseline,
`hidden_size=1296, n_layers=1`, без регуляторов коммуникации у этого
семейства в принципе).

**Бюджет:** `n_steps=1.0e9`, `n_envs=512`, `rollout_len=32` — идентично
основным прогонам статьи, только с новым кодом оценки.

**Команды (после реализации (a)+(b) в коде):**
```sh
ssh aicenter3 'cd /storage/annenkov_vd/knitwork && CUDA_VISIBLE_DEVICES=3 \
  nohup .venv/bin/python knitwork/exps/sdq/run.py \
  knitwork/exps/sdq/config/large.yaml --model=grnn.L2C4 \
  name="grnn_L2C4_fixedgap_sdq_E2" \
  > /storage/annenkov_vd/knitwork/logs/E2_L2C4.log 2>&1 &'
# аналогично --model=grnn.L3C4 и --model=rnn.L1
```

**Ожидаемые ресурсы:** разработка (a)+(b) — до 0.5 дня (не GPU-время). После
этого — 3 прогона на H100, ориентировочно по ≈30-60 минут каждый
(`rnn.L1` с `hidden_size=1296` вероятно медленнее compact grnn-форм —
закладывать верхнюю границу).

**Почему это нужно.** Единственная content-level претензия из всего списка,
которую **не заметил** ни один человеческий рецензент AAAI-27 — только
AI-Reviewer: «"long gap" relative to the current batch mean, which varies
with the online curriculum… fixed-gap and common out-of-distribution
evaluations are needed». Порог «выше среднего по батчу» — плавающая
величина: одно и то же абсолютное значение gap в начале curriculum (T≈10)
считается «длинным», а в конце (T≈500) — «коротким»; метрика меняет смысл в
процессе самого обучения, которое она измеряет. Это методологический дефект
метрики, не вопрос формулировки. Новый набор рецензентов (AISTATS) может
прочитать раздел Metric внимательнее, чем это сделали рецензенты AAAI-27.

## 4. Эксперимент E3 — top-k routing ablation (M-3, частичный ответ на RIMs/BRIMs)

**Код: НЕ реализован, баг подтверждён на текущей HEAD.**
`knitwork/models/grnn_core.py:51-63` передаёt `n_q`/`n_kv` всем трём
вариантам message-passing слоя:
```python
mhas = [MessagePassingLayer, MessagePassingLayer1, StochasticMessagePassingLayer]
mha = mhas[mha]
...
self.attn.append(mha(
    self.hidden_size, num_heads=self.n_attn_heads, ln_msg=ln_msg,
    n_q=self.n_columns, n_kv=self.n_columns + self.n_inputs, **mha_kwargs,
))
```
но `MessagePassingLayer`/`MessagePassingLayer1` (`grnn_core.py:312`, `:370`)
принимают `n_participants`, не `n_q`/`n_kv` — `mha=0`/`mha=1` падают с
`TypeError` до начала обучения (это ловится smoke-test'ом из §0, не тратит
GPU-время впустую, но всё равно блокирует эксперимент).

**Требуемая правка (рекомендованный вариант):** добавить в
`StochasticMessagePassingLayer` (рабочий роутер, `mha=2`, тот же, что
используется во всех текущих прогонах) необязательный параметр
`top_k: int | None = None`, маскирующий перед softmax все логиты, кроме
top-k по последней размерности (`torch.topk` + `masked_fill(-inf)`), не
трогая остальную логику (noise, β). Оценка: ≈20-40 строк, не починка двух
legacy-классов с неизвестным объёмом скрытых расхождений.

**⚠️ Требует явного согласия пользователя перед правкой** — `grnn_core.py` не
входит в защищённый список `CLAUDE.md` (`grnn.py`, `grnn_err.py`, `gru.py`,
`config/base.yaml`), но меняет поведение модели, уже давшей числа для
поданной на AAAI-27 версии статьи.

**Модель и гиперпараметры:** `grnn.L2C4`, те же базовые параметры, что в E1,
плюс `grnn_L2C4.top_k=1` после реализации.

**Бюджет:** `n_steps=1.0e9`, идентично основным прогонам.

**Команда (после фикса):**
```sh
ssh aicenter3 'cd /storage/annenkov_vd/knitwork && CUDA_VISIBLE_DEVICES=3 \
  nohup .venv/bin/python knitwork/exps/sdq/run.py \
  knitwork/exps/sdq/config/large.yaml --model=grnn.L2C4 \
  grnn_L2C4.top_k=1 name="grnn_L2C4_topk1_sdq_E3" \
  > /storage/annenkov_vd/knitwork/logs/E3_sdq.log 2>&1 &'
# аналогично для text8 (knitwork/exps/text/run.py + config/large.yaml)
```

**Ожидаемые ресурсы:** разработка — 2-4 часа (не GPU). 2 прогона на H100,
≈25-50 минут каждый (оценка как в E1).

**Почему это нужно.** Dpwf прямо: «closely related to RIMs, BRIMs, and
relational memory models, but there is no direct comparison with these
methods». Полная реимплементация этих архитектур нереалистична в срок
(отдельная система sparse-активации подмножества модулей, не переиспользуема
из текущего кода — см. Приоритет C ниже). Top-k ablation внутри собственной
архитектуры — не «MoSAIC vs RIMs» напрямую, но отвечает на механическую
часть претензии («обязательна ли плотная маршрутизация, или разреженная
работает так же»), переводя её из «вообще никаких данных» в «направленный,
пусть не исчерпывающий, ответ».

## 5. Эксперимент E4 — нормализация `extra_w` + перезапуск L2C16

**Код: НЕ реализован (1 строка), требует согласия пользователя.**
`knitwork/models/grnn_core.py:204-213`:
```python
prob_comm = 1.0 - pi_route.diagonal(dim1=-2, dim2=-1)
comm_loss = prob_comm
...
extra_w = torch.arange(Cq, dtype=pi_route.dtype, device=pi_route.device).view(1, -1)
x_ext_prob_weighted = pi_route[..., -1] * (extra_w * 2 - 1)
comm_loss = prob_comm + x_ext_prob_weighted
```
При `Cq=16` веса по колонкам — `-1, 1, 3, ..., 29`, тогда как `prob_comm`
ограничен `[0, 1]` — штраф для последней колонки доминирует над основным
сигналом на два порядка. **Фикс:** нормировать на число колонок —
`x_ext_prob_weighted = pi_route[..., -1] * (extra_w * 2 - 1) / Cq`.

**⚠️ Требует явного согласия пользователя перед правкой** (та же оговорка,
что и в E3 — файл не защищён формально, но уже дал числа для AAAI-27).

**Модель и гиперпараметры:** `grnn.L2C16` (`hidden_size=224, n_layers=2,
n_columns=16, n_attn_heads=4, noise_std=0.02` SDQ / `0.05` text8) — без
других изменений, кроме фикса в коде.

**Бюджет:** `n_steps=1.0e9`, идентично основным прогонам.

**Команды (после фикса):**
```sh

  nohup .venv/bin/python knitwork/exps/sdq/run.py \
```

**Почему это нужно.** Даёт прямой, количественный ответ на претензию «state

## 5.1. Эксперимент E5 — state-matched GRU control (прямой ответ на claim 1 / Владимир)

Добавлено по итогам переписки Petr/Владимира (01.10.2026, см. §9) — Владимир
прямо просит контроль с выровненным **размером активационного состояния**
(не только параметров). **Это дешевле всех остальных новых экспериментов в
этом файле: код уже есть, не требует ни одной новой строки.**

**Код: полностью реализован.** Используется тот же `rnn.<L>` (GRU-baseline
из реестра `knitwork/models/utils.py`), только с другим `hidden_size`,
подобранным под целевой размер state (не под целевое число параметров, как
в текущих Table 1/2).

**Модель и гиперпараметры — пересчёт `hidden_size` под совпадение `L·H` с
`L·C·H` у MoSAIC:**

| Контроль | Базовая форма MoSAIC | Целевой state (`L·C·H`) | GRU `L` | GRU `H'` (решение `L·H'=target`) |
|---|---|---|---|---|
| state-matched vs L2C4 | grnn.L2C4 (L=2,C=4,H=424) | 3392 | 2 | **1696** |
| state-matched vs L3C4 | grnn.L3C4 (L=3,C=4,H=344) | 4128 | 3 | **1376** |

Точные значения `H'` — из прямого решения уравнения, **не из округления**;
перед запуском проверить фактическое число обучаемых параметров через
`knitwork/common/count_params.py` (или просто по стартовому логу `run.py`,
который печатает число параметров) — при таком `H'` GRU неизбежно выйдет
**значительно за пределы ~10M параметров** (квадратично от `H`, ожидаемо
в несколько раз больше, точное число — проверить эмпирически, не считать
заранее более точно, чем позволяет формула).

**Бюджет:** `n_steps=1.0e9`, остальные параметры (`n_envs`, `rollout_len`,
LR-график, curriculum) — идентичны основным прогонам GRU в `large.yaml`, не
меняются.

**Команды:**
```sh
ssh aicenter3 'cd /storage/annenkov_vd/knitwork && CUDA_VISIBLE_DEVICES=3 \
  nohup .venv/bin/python knitwork/exps/sdq/run.py \
  knitwork/exps/sdq/config/large.yaml --model=rnn.L2 rnn_L2.hidden_size=1696 \
  name="rnn_L2_statematched_vs_L2C4_sdq_E5" \
  > /storage/annenkov_vd/knitwork/logs/E5_sdq_L2.log 2>&1 &'
# аналогично --model=rnn.L3 rnn_L3.hidden_size=1376 (vs L3C4),
# и аналогично для text8 (knitwork/exps/text/run.py + config/large.yaml)
```
4 прогона всего (2 формы × 2 задачи).

**Ожидаемые ресурсы:** модель заметно шире (`H'=1696` против текущего
максимума `H=1296` у `rnn.L1`) — закладывать **верхнюю границу оценки
времени** (§7.1), возможно выше ≈60 минут, т.к. более широкий GRU на batched
matmul может оказаться медленнее по шагам, чем любой из текущих прогонов;
подтвердить замером, не просто экстраполяцией.

**Почему это нужно.** Table 3 статьи документирует разницу в state size, но
не контролирует её — ни одна строка таблицы не показывает GRU с таким же
state, как у MoSAIC. Это прямой, количественный ответ на claim 1 (Dpwf: «the
gains cannot be clearly attributed to modular organization or learned
communication» без state-matched control). Не отменяет параметрически
матченную Table 1/2 — **добавляется как отдельная, явно помеченная
строка/мини-таблица** («state-matched control, ~X× more parameters»), а не
подменяет существующее сравнение. Если при равном state GRU всё ещё хуже
MoSAIC — это сильный, прямой контраргумент на claim 1 (модульность даёт
выигрыш даже без выигрыша в параметрах ИЛИ в state). Если GRU догоняет —
это тоже честный и важный результат, который нужно включить как есть, а не
отбрасывать прогон.

**Альтернативная позиция (зафиксировать в тексте как secondary framing,
независимо от результата E5).** Petr в той же переписке прямо выразил
сомнение в самой валидности state-matching как критерия: «звучит как-то
глупо сравнивать по размеру стейта, тк физические ограничения на память
обычно и на скорость, а не на то какого размера стейт». Это не повод
пропустить E5 (claim 1 нужно закрыть данными, а не только аргументом), но
это валидный **дополнительный** довод для текста статьи: throughput/память
(claim 7, `text-and-format-fixes.md` §2, числа уже есть в Comet) —
физически более релевантная метрика ресурсных ограничений, чем число
state-скаляров как таковое. Обе рамки (state-matched control числом + довод
про физические ограничения) можно привести вместе, они не противоречат друг
другу.

## 5.2. Эксперимент E3-ext — модульная sparse-активация (приближение к RIM/BRIM)

Также по итогам переписки — Владимир считает, что RIM/BRIM-аналоги
придётся прогнать, т.к. это прямые related works. **E3 (top-k routing,
§4) уже покрывает механическую суть различия MoSAIC/RIMs (dense vs sparse
routing), но это не полный аналог RIMs** — у RIMs разреженность не только в
том, *откуда* модуль получает сообщение, а в том, *обновляется ли вообще*
состояние неактивного модуля на этом шаге (inactive modules freeze their
state). E3 в текущей постановке (`top_k` маскирует только логиты
внимания/источники сообщений) этого не делает — все колонки всё равно
проходят свой GRU-шаг каждый раз.

**Код: не реализован, отдельная (большая, чем E3) правка.** Нужно: (а) после
получения маршрутизированного сообщения вычислить per-column
activation-score (например, норма сообщения или отдельный learned gate); (б)
выбрать top-k активных колонок per layer per step; (в) для неактивных
колонок **не выполнять** `GRU_{l,c}(x, h_{t-1})`, просто пронести
`h_t = h_{t-1}` (frozen state). Это полноценная архитектурная модификация
`grnn_core.py`, не косметическая правка, как в E3/E4.

**⚠️ Требует явного согласия пользователя** (та же причина, что в E3/E4 —
плюс здесь риск выше: это самая крупная по объёму правка кода из всего
плана).

**Модель и гиперпараметры:** `grnn.L2C4`, `top_k_active ∈ {2, 3}` из 4
колонок (RIMs типично активируют ~50% модулей — для `C=4` это 2; стоит
проверить обе точки, если время позволяет).

**Бюджет:** `n_steps=1.0e9`, идентично остальным прогонам.

**Ожидаемые ресурсы:** разработка — **реалистично больше 0.5 дня**, в
отличие от E3 (которая была оценена в 2-4 часа) — это новый вид операции
(условное обновление state по маске, а не просто маскирование softmax),
плюс отладка влияния на backward pass (неактивные колонки не должны
получать градиент через GRU на этом шаге, но должны участвовать в будущих
шагах как query/источник). **Это единственный пункт всего плана (оба
файла), который реалистично может не влезть в оставшиеся дни** — честная
оценка риска, не оптимистичная.

**Почему это нужно.** Это настоящий, а не частичный ответ на claim 3 — не
«дали максимально похожий на RIMs механизм внутри своей кодовой базы», а
«реализовали определяющее архитектурное свойство RIMs (conditional/sparse
module update) и сравнили». Без этого E3 остаётся честным, но ограниченным
ответом («routing sparsity», не «module-update sparsity») — такое
разграничение нужно явно проговорить в тексте статьи в любом случае (даже
если E3-ext выполнится), т.к. иначе рецензент, знающий RIMs детально, может
счесть сравнение неполным.

**Позиционная заметка (zero-compute, не требует E3-ext для использования).**
MoSAIC по структуре уже ближе к **BRIMs**, чем к RIMs — BRIMs добавляют
иерархическую bottom-up/top-down коммуникацию (Mittal et al. 2020), и
`grnn_core.GridRnn` **уже имеет** top-down feedback (нижний слой читает
отложенные состояния верхнего слоя с предыдущего шага) наряду с bottom-up
within-timestep коммуникацией. Это стоит явно проговорить в Related Work
как структурное сходство с BRIMs (а не только различие с RIMs) — это
усиливает заявку на относящуюся к делу новизну, не ослабляет её, и не
требует вообще никакого нового кода или прогона — чисто текстовая правка в
Related Work статьи, выполнимая независимо от того, успеет ли E3-ext.

## 6. Приоритет C — явно НЕ делать, зафиксировать как Limitations

Явно исключены из плана, независимо от доступных ресурсов — не из-за
нехватки мощности, а из-за объёма разработки/дизайна, несовместимого со
сроком подачи. **Обновлено по итогам §9: RIM/BRIM полностью исключить из
Приоритета C не удалось — команда намерена попытаться (E3-ext, §5.2), но
граница проведена на уровне «определяющий механизм (sparse module update),
не вся опубликованная архитектура целиком».**

- **Полная переоценка HGRN2/DeltaNet/mLSTM на 1B токенов (M-4).** Три
  модели × минимум 1 полный прогон на 1B токенов каждая — даже на H100 это
  не вопрос GPU-часов (см. §7 ниже, компактные модели почти не насыщают
  карту), а вопрос последовательной разработки/валидации трёх внешних
  baseline-реализаций на новом масштабе. Решение: оставить как
  «reduced-token context, explicitly non-comparable» (формулировка — в
  `text-and-format-fixes.md`).
- **Полная реимплементация RIMs/BRIMs/Relational Memory Core целиком** (их
  собственные LSTM-варианты, input attention, communication attention как
  двухуровневая система) — всё ещё явно исключена: это кратно больше, чем
  E3-ext. Минимально достаточный, согласованный с командой ответ — E3
  (routing sparsity) + E3-ext (module-update sparsity), §5.2.
- **Scaling study на большем масштабе / другие задачи (мини-pile, text9,
  Craftax/Crafttext).** Упомянуты в переписке команды как параллельно
  идущая работа — это не входит в экспериментальный бюджет текущей заявки
  на AISTATS 2027, если не дойдёт до публикуемого состояния до 06.10.2026
  самостоятельно (см. §9). Ответ для этой конкретной заявки — только
  текстовое сужение claim (`text-and-format-fixes.md` §2, claim 6).
- **RL-раздел / MIKASA runs.** Не относится к этой статье вообще (отдельный
  проект, `article/future_work.md`) — не экспериментальная задача, а
  решение убрать упоминание из Limitations (см. пару-файл).

доступен **только** `aicenter3`/GPU 3 (по новой инфраструктурной политике из
`CLAUDE.md`) — это *ограничение* по сравнению с
исторической гибкостью, не улучшение, и однородность устройства (все новые
прогоны на одном и том же H100) на самом деле облегчает сравнение
результатов между репликами (меньше device-to-device дисперсии, которая
явно видна в таблице выше — например `grnn.L2C4`/`rnn.L1` на SDQ имеют σ
loop-time до ±1.14ч именно из-за смешанных устройств).

### 7.2. Требуемые мощности — сколько H100 реально нужно (обновлено)

**Одной H100 достаточно с большим запасом** — вывод не изменился, но теперь
подтверждён измерением, а не инженерной экстраполяцией. VRAM не является
узким местом (модели ~10M параметров, H100 — 80 GB) — весь набор из 11-19
прогонов (§7, с учётом §9 по E1/E3-ext) технически можно запустить
**одновременно, одним пакетом**, если доступен весь GPU 3. При полном
параллелизме суммарное время сводится к времени самого долгого одного
прогона (**до ≈2.3 ч**, по измеренным данным §7.1, не ≈1 ч как в предыдущей
версии) — то есть весь вычислительный план укладывается **в несколько
часов**, если GPU 3 свободна на это время.

**Единственное реальное ограничение — то, что GPU 3 на `aicenter3` общая, не
выделенная под этот проект**, и, по историческим данным §7.1, проект и
раньше распределял прогоны по нескольким физическим машинам, когда
единственная карта была занята. Практическая рекомендация не изменилась:
проверять `nvidia-smi -i 3` перед каждым запуском, закладывать в расписание
возможность ожидания освобождения карты, а не только время самих прогонов.

**Если оценка ×2-×5 из предыдущей версии этого раздела использовалась
где-то ещё (например, в черновике статьи или в обсуждении с командой) —
заменить на измеренные числа выше.** Инженерная экстраполяция больше не
нужна как источник этих чисел.

**Оговорка.** Оценка ×2-×5 ускорения — инженерная экстраполяция по профилю
нагрузки, не измерение на этом конкретном коде на H100. Сделать замер —
